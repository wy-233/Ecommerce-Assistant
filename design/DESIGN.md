# Ecommerce Assistant 前端视觉方案

> 交付物：`design/index.html`（单文件，可直接双击在浏览器打开）
> 对应 PRD：`docs/PRD.md` v0.3（第一阶段 MVP；前端契约自 v0.2 起保持兼容）

## 1. 视觉主张

这个产品的本体是一台**分拣机**：用户丢来一个问题，助手识别意图，把它送到四条处理链之一。

所以整套界面不用「客服后台」的通用语言（侧栏导航 + 卡片列表 + 聊天气泡），而是用**分拣中心**的语言：运单头、传送带、道口、投递的包裹。页面上唯一的高饱和元素是四条道的**编码色**——它不是装饰，是信息：同一条道的颜色在分拣带、消息边缘、来源引用块上恒定出现。

一句话概括：**颜色是路牌，不是油漆。**

## 2. 设计 token

### 颜色

| 名称 | 值 | 用途 |
| --- | --- | --- |
| paper | `#E7E8E2` | 页面底色，冷调再生纸白 |
| card | `#FBFBF8` | 白卡纸：道口、回执块、输入框、运单头 |
| ink | `#171A1F` | 条码墨：正文、传送带、主按钮 |
| ink-2 | `#3C4046` | 次级正文 |
| mute | `#63675E` | 标签、辅助值、占位符 |
| rule | `#C7C9C0` | 1px 分隔线 |
| route-after | `#C4400C` | 售后 / 商品 → RAG 知识库 |
| route-order | `#2F4BC4` | 订单 → order_lookup |
| route-stock | `#3F6B3A` | 库存 → stock_lookup |
| route-ship | `#8F6410` | 物流 → shipping_lookup |
| 兜底底纹 | `#FBEFE8` | 未识别回执的背景 |

四条道色同时用于色块与文字，均已按 AA 标准校验（见第 4 节）。

### 字体

| 角色 | 字族 | 说明 |
| --- | --- | --- |
| 拉丁（标题 + 正文） | Archivo | 工业感的无衬线，字重谱系宽，不做「一个词换色/斜体」那类强调 |
| 中文 | Noto Sans SC | 400 / 500 / 700 |
| 数据 | DM Mono | 单号、SKU、工具签名、`thread_id`、`run_id` |

基字重 400，15px / 1.62。道口名与 h1 用 600-700，其余靠字号与间距拉层次。

对齐规则：全部左对齐。h1 与说明文字限宽 22ch / 58ch；回执正文限宽 72ch（中文约 34 字/行）。道口等宽 4 列、间距 12px，与传送带构成一组。

### 原则

1. **颜色即信息**：道色只出现在「这条问题被送到哪条道」的地方，不做氛围色。
2. **一个记忆点**：分拣带。其余元素保持安静、无阴影、无渐变。
3. **真实语汇**：字段名用面单写法（`thread`、`run_id`、`order_lookup`），不用泛化的 SaaS 措辞。
4. **一次编排好的动效**：页面加载时四道口依次淡入（60ms 间隔），此后只有用户提问才触发包裹投递。
5. **纪律**：沿用 70Materia 的约束——0 圆角（按钮 3px）、无阴影、无渐变、字重以 400 为基。

## 3. 对照 brief 的自检

| 常见 AI 默认 | 本方案的处理 |
| --- | --- |
| 暖奶油底 `#F4F1EA` + 陶土色 `#D97757` | 底改为冷调 `#E7E8E2`；强调色是四色编码系统而非单一暖橙 |
| 近黑底 + 荧光强调 | 全程浅色。深色只用于传送带与主按钮，占比极小 |
| 每张卡统一圆角 + 同款阴影 | 无阴影；圆角仅按钮 3px，其余直角 |
| 内容切成一模一样的圆角卡片 | 道口是信息编码格，回执是票据块，两者形态不同 |
| 每个标题上方全大写 eyebrow 标签 | 中文标签直接用字重和字距拉层次；等宽大写仅用于代码类数据 |
| 01 / 02 / 03 编号 | 不用。四条道是并列通道，不是序列 |
| 每节 fade-and-slide-up | 仅页面加载一次；其余动效只响应用户提问 |
| 标题里单独高亮一个词 | 不用。h1 整体同色同重 |
| 链接和按钮末尾加 `→` | 不用 |

做过但删掉的：初稿在每条消息前放了流水号，读起来像「01/02/03」，且编号不承载信息。改为左边缘道色条，一个元素同时承担角色区分与路由结果。

## 4. 质量基线

- **对比度**：正文 `#3C4046`/`#E7E8E2` ≈ 8.5:1。初审时发现两处不达标并已修正——次级文字 `#7E827A` 仅 3.18:1，改为 `#63675E`（4.7:1）；物流道赭黄 `#A8761A` 在回执头条上仅 3.84:1，改为 `#8F6410`（5.1:1）。
- **键盘**：所有交互元素可 Tab 到达，`:focus-visible` 用 2px 墨色描边。来源引用用原生 `<details>`，键盘可展开。
- **动效**：`prefers-reduced-motion: reduce` 时全部动画与过渡降为 0.01ms，包裹投递改为直接跳过。
- **响应式**：1080px 断点下轨迹栏移至正文下方并横排；760px 下分拣带变 2×2、回执取消限宽；600px 下快捷问题横向滚动。
- **语义**：主对话区 `aria-live="polite"`，分拣带与轨迹栏为具名 `<aside>`/`<section>`，装饰性包裹 `aria-hidden`。

自查方式：逐张截图比对（桌面 1460 / 移动 390 / 投递过程中），核对道口激活态、计数递增、兜底回执配色与包裹落点。

## 6. 接入后端

文件内 `API_BASE` 默认为空，此时使用内置演示数据，页面可脱离后端直接预览。指向 FastAPI 服务后即走真实链路：

```js
var API_BASE = "http://localhost:8084";

// 走 POST /ecommerce-assistant/invoke，请求体 { message, thread_id, user_id }
// 响应按 ChatMessage 读取 content / route / tool_calls / sources / run_id（PRD v0.2 6.7.1）
```

前端不自行判断路由：`route` 一律以后端返回为准，仅据此决定分拣带计数、道口高亮与配色。原型内用于脱离后端预览的关键词匹配只是演示手段，**不得移植为实现**。

前端不再自行判断路由，一律呈现后端返回的结果；仅在请求失败时用兜底回执说明原因。SSE 流式（`/ecommerce-assistant/stream`）尚未接入，如需逐 token 渲染可在 `handleViaBackend` 基础上替换为 `EventSource` 或 `fetch` 流读取。
